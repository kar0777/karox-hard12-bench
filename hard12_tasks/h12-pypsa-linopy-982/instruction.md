### Issue Description

`Model.copy()` turns every frozen `CSRConstraint` into a dense `Constraint`, while the copy keeps `freeze_constraints=True`. The copy is therefore no longer sparse, without any message, and constraints added to the copy afterwards are frozen again, so one model ends up with both kinds.

Cause: `copy` rebuilds each constraint as `Constraint(con.mutable().data, ...)` ([`linopy/io.py:1380-1390`](https://github.com/PyPSA/linopy/blob/b9a698bed8ab561a5840d17bf8843c07172eb700/linopy/io.py#L1380-L1390)).

### Reproducible Example

```python
import pandas as pd

import linopy

m = linopy.Model(freeze_constraints=True)
x = m.add_variables(lower=0, coords=[pd.RangeIndex(3, name="i")], name="x")
m.add_constraints(x >= 1, name="c")

c = m.copy()
print(type(m.constraints["c"]).__name__, m.freeze_constraints)
print(type(c.constraints["c"]).__name__, c.freeze_constraints)
```

Output on master (b9a698be):

```
CSRConstraint True
Constraint True
```

### Expected Behavior

A frozen constraint stays a `CSRConstraint` in the copy (copying its CSR store, respecting `deep=` and `include_solution=`), and a dense constraint stays dense. Relevant for #976, which proposes that a copy of a sparse model stays sparse.
